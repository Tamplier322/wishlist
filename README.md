# Wishlist

Веб-приложение для списков желаний. Можно собирать вещи в списки, делиться ими с друзьями и родственниками, бронировать подарки, чтобы не подарить одно и то же дважды, и следить за ценами.

Демо: https://wishlist-xre9.onrender.com

## Возможности

- Списки желаний с категориями, приоритетами, поиском, фильтрами и сортировкой.
- Добавление по ссылке: название, картинка и цена подтягиваются с сайта магазина.
- Цены в BYN, USD, EUR и RUB. В профиле выбирается своя валюта, и все цены в списках показываются в ней. У отдельного желания валюту можно поменять.
- Загрузка своей картинки или автоматический подбор изображения.
- Совместные списки до пяти человек. У каждого участника свой цвет, приглашение по имени пользователя или по ссылке.
- Бронь подарка: видно, кто что забронировал. Снять чужую бронь может только владелец списка.
- Комментарии к желаниям, в том числе скрытые от автора списка.
- Обновления в реальном времени: изменения сразу появляются у всех участников.
- Публичная ссылка на список, смотреть можно без регистрации.
- Гостевой режим: попробовать без аккаунта, список хранится в браузере.
- Импорт и экспорт списка текстом, а также карточка списка в PNG.
- Дедлайн с обратным отсчётом.
- Уведомления в браузере: бронь, покупка, новые желания.
- Установка как приложение на телефон, тёмная тема, русский и английский язык.

## Технологии

Фронтенд: React, TypeScript, Redux Toolkit и RTK Query, Socket.IO, Vite.

Бэкенд: Node.js, Express, TypeScript, Socket.IO, zod, firebase-admin.

Данные: Firebase Firestore. Для локального запуска и тестов используется SQLite, чтобы не нужен был облачный аккаунт.

Тесты: Playwright.

## Запуск локально

Понадобится Node.js 20 или новее.

```bash
git clone https://github.com/Tamplier322/wishlist.git
cd wishlist
npm install
npm run dev:server
npm run dev:client
```

Сервер запустится на http://localhost:4000, клиент на http://localhost:5173. Запросы к API проксируются с клиента на сервер.

Без настроенного Firebase приложение работает на локальной базе SQLite. Файл базы и папка для загруженных картинок создаются сами при первом запуске.

## Настройка Firebase

Для работы с Firestore нужен ключ сервисного аккаунта из консоли Firebase, раздел Project settings, вкладка Service accounts.

Локально достаточно положить файл ключа в `server/firebase-service-account.json` и запустить сервер с переменной `FIREBASE_SERVICE_ACCOUNT_FILE`, указав путь к этому файлу.

На сервере ключ удобнее передать переменной окружения `FIREBASE_SERVICE_ACCOUNT` в виде base64 от содержимого JSON. Так значение не содержит кавычек и переводов строк и не обрезается при вставке. Подойдут и отдельные переменные `FIREBASE_CLIENT_EMAIL` и `FIREBASE_PRIVATE_KEY`.

Ключ в репозиторий не попадает, он указан в `.gitignore`.

## Вход через Google и Telegram

Помимо входа по логину и паролю поддерживаются два внешних сервиса. Кнопки появляются на `/login` и `/register`, если соответствующие переменные заданы на сервере; иначе блок скрывается. В профиле (`/profile` → «Способы входа») сервис можно подключить к существующему аккаунту или отключить.

Что нужно задать:

| Сервис       | Переменные                                       | Redirect URI                                                    |
| ------------ | ------------------------------------------------ | --------------------------------------------------------------- |
| Google       | `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`       | `<PUBLIC_API_URL>/api/auth/oauth/google/callback`                |
| Telegram     | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`    | не нужен — используется Login Widget с проверкой HMAC-подписи    |

Как получить ключи:

1. **Google** — [Google Cloud Console](https://console.cloud.google.com/) → APIs & Services → Credentials → Create credentials → OAuth client ID → Web application. В «Authorized redirect URIs» добавьте callback выше. Для локальной разработки используйте `http://localhost:4000/api/auth/oauth/google/callback`.
2. **Telegram** — [@BotFather](https://t.me/BotFather) → `/newbot` (или существующий бот) → `/setdomain` → укажите домен приложения (`localhost` для разработки). В `TELEGRAM_BOT_USERNAME` укажите имя бота без `@`.

Безопасность OAuth: authorization code + PKCE (S256), подписанный `state` с одноразовым nonce в HttpOnly-cookie, проверка подписи Google ID-token по JWKS, проверка HMAC и свежести Telegram-подписи, защита от replay. Токены не передаются в URL: после callback клиент обменивает одноразовый код через `POST /api/auth/oauth/exchange`.

Если аккаунт с таким же подтверждённым email уже существует, автоматическая привязка **не** выполняется (защита от захвата аккаунта): нужно войти паролем и подключить сервис в профиле. Отключить последний способ входа нельзя — сначала задайте пароль или подключите другой сервис.

## Пароль и журнал входов

- **Пароль для OAuth-аккаунта.** Если аккаунт создан только через Google или Telegram, в профиле доступна форма «Задать пароль». После установки можно входить по почте. Смена существующего пароля требует текущий пароль и **отзывает все остальные сессии** — текущая получает новую пару токенов.
- **Журнал безопасности.** Раздел «Безопасность аккаунта» в профиле показывает последние 20 событий: вход по паролю, неудачные попытки, OAuth-входы, установку пароля и срабатывание reuse-detection.

Эндпоинты: `POST /api/auth/password`, `GET /api/auth/security/events`.

## Деплой на рендере

В корне проекта есть `render.yaml`. Создаётся один веб-сервис, который раздаёт собранный фронтенд и API.

Команда сборки: `npm install && npm run build`. Команда запуска: `npm start`.

В настройках сервиса нужно задать `JWT_SECRET` и один из вариантов ключа Firebase, описанных выше. После деплоя приложение доступно по адресу сервиса.

## Тесты

```bash
# unit-тесты сервисов (vitest, in-memory SQLite)

# сборка и проверка типов
```

## Наблюдаемость

- Логи — структурный JSON через `pino`/`pino-http`; у каждого запроса есть `x-request-id` (принимается из заголовка или генерируется), пароли и токены вырезаются.
- Метрики — `GET /metrics` в формате Prometheus: длительность и количество HTTP-запросов, ошибки провайдеров предложений, системные метрики процесса. При заданном `METRICS_TOKEN` нужен `?token=`.
- Алерты — правила в [`monitoring/prometheus-alerts.yml`](monitoring/prometheus-alerts.yml): доля 5xx, p95 latency, падения провайдеров, недоступность сервиса.
- Трейсинг — при заданном `OTEL_EXPORTER_OTLP_ENDPOINT` включается OpenTelemetry с автоинструментированием HTTP, Express и Firestore.

## Бэкапы и staging

- Ежедневный экспорт Firestore в GCS — workflow [`.github/workflows/firestore-backup.yml`](.github/workflows/firestore-backup.yml). Нужны секреты `GCP_SERVICE_ACCOUNT_JSON`, `GCP_PROJECT_ID`, `FIRESTORE_BACKUP_BUCKET`; бэкапы старше 30 дней удаляются.
- Preview/staging — в `render.yaml` включены preview environments: каждый PR получает отдельный инстанс со своими переменными (`METRICS_TOKEN`, `OTEL_EXPORTER_OTLP_ENDPOINT`), которые не синхронизируются с продом.

## Безопасность

- **Пароли** — bcrypt (12 раундов), минимум 8 символов с буквами и цифрами, отсев частых паролей; защита от перебора по паре «IP + логин» и выравнивание времени ответа, чтобы нельзя было определить существование аккаунта.
- **Сессии** — короткоживущий access-JWT (15 минут) с проверкой алгоритма, issuer, audience и типа токена; refresh-токены хранятся только в виде SHA-256-хеша и ротируются при каждом обновлении. При повторном использовании уже отозванного refresh-токена (reuse-detection) отзываются **все** сессии пользователя и событие попадает в журнал безопасности.
- **OAuth** — PKCE S256, подписанный одноразовый state + HttpOnly SameSite=Lax cookie, проверка подписи Google ID-token по JWKS, HMAC-подпись и ограничение возраста Telegram-данных, защита от replay, одноразовый код обмена на токены.
- **Заголовки** — helmet: CSP (в проде), HSTS, `X-Content-Type-Options`, `Referrer-Policy`, запрет фрейминга; `x-powered-by` отключён; строгий CORS-allowlist (и для Socket.IO).
- **SSRF** — `image-proxy` и разбор пользовательских ссылок ходят через `safeFetch`: только http(s), запрет localhost/приватных IP и metadata-сервисов, закрепление DNS-ответа, ручная проверка редиректов, лимит размера.
- **Загрузки** — ограничение 5 МБ, белый список MIME и проверка «магических байтов», случайное имя файла; отдача с `nosniff`, `Content-Disposition: inline` и sandbox-CSP; ссылки подписаны и истекают.
- **Данные** — все запросы к БД параметризованы; доступ к спискам проверяется на сервере (владелец/участник); правила Firestore запрещают любой прямой доступ из браузера; секреты редактируются в логах.
- **Конфигурация** — в продакшене `assertSecureConfig` громко логирует dev-секрет JWT, отсутствие CORS и http-адреса; публичные адреса и CORS на Render автоматически берутся из `RENDER_EXTERNAL_URL`.
